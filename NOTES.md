## Inbound: tun

```json
"address": ["172.18.0.1/30"]
```
Адрес самого туннельного интерфейса. `/30` — минимальная сеть, где есть
пригодный адрес; больше и не нужно, через интерфейс не адресуется ничего кроме
него самого.

Взято `172.18.x`, а **не** `172.19.x` намеренно: Hiddify держит `utun5` с адресом
`172.19.0.1/28`. Разные подсети означают, что при случайном одновременном запуске
конфликта адресов не будет — а Hiddify мы оставляем как запасной вариант.

Поле `address` появилось в 1.10.0 и заменило `inet4_address`/`inet6_address`.
Старые поля в 1.13.16 не просто устарели — они дают **фатальную ошибку старта**
(в коде явная проверка). Документация в этом месте отстала и всё ещё показывает
их в структуре с пометкой «будет удалено в 1.12.0»; удаление уже состоялось.

```json
"mtu": 9000
```
Документация 1.13 не даёт **никаких** рекомендаций по MTU и не называет значение
по умолчанию. По коду умолчание для CLI на macOS — 65535.

9000 выбрано не наугад. В `protocol/tun/inbound.go` есть darwin-специфичная
оптимизация:

```go
multiPendingPackets := C.IsDarwin && ((options.Stack == "gvisor" && tunMTU < 32768) ||
                                      (options.Stack != "gvisor" && options.MTU <= 9000))
```

То есть при `stack: mixed` и MTU ≤ 9000 включается режим `EXP_MultiPendingPackets`,
а при умолчании 65535 — нет. Заодно 9000 — единственное значение MTU, которое
встречается в примерах официальной документации. Hiddify, к слову, использует то же.

```json
"auto_route": true
```
На macOS работает не через `0.0.0.0/0`. Из `sing-tun/tun_rules.go`:
`autoRouteUseSubRanges = runtime.GOOS == "darwin"` — вместо одного маршрута
ставятся **восемь**, покрывающих всё адресное пространство:

```
1.0.0.0/8  2.0.0.0/7  4.0.0.0/6  8.0.0.0/5
16.0.0.0/4 32.0.0.0/3 64.0.0.0/2 128.0.0.0/1
```

Так сделано, чтобы не перебивать системный `default`, а выиграть у него по длине
префикса. Именно эти восемь строк вы видите в `netstat -rn` при работающем
туннеле — и именно их удаляет `emergency-reset.sh`.

Маршруты ставятся сообщениями `RTM_ADD` в `PF_ROUTE`-сокет и снимаются в
`unsetRoutes()` при штатной остановке. **При `SIGKILL` или падении процесса
снятие не выполняется** — маршруты остаются в ядре, и весь трафик уходит в
исчезнувший интерфейс. Отсюда `emergency-reset.sh` и настойчивость с `SIGTERM`.

```json
"strict_route": false
```
Вы просили его включить, но на macOS он **не делает ничего**. Раздел документации
описывает поведение только для Linux и Windows; про macOS там нет ни слова.
Проверка по исходникам: идентификатор `StrictRoute` встречается в `tun.go`
(объявление), `tun_linux.go`, `tun_windows.go` и `redirect_nftables_rules.go` —
в `tun_darwin.go` **ни разу**.

Поставить `true` безвредно, но это создало бы ложное ощущение защиты от утечек,
которой на macOS нет. Оставлено `false` осознанно.

```json
"stack": "mixed"
```
Умолчание при сборке с тегом `with_gvisor` — а он есть в нашем бинарнике
(проверено: `sing-box version` показывает `with_gvisor` в списке тегов).
`mixed` = системный TCP-стек + gVisor для UDP. Задано явно, чтобы значение не
поехало при пересборке.

**`interface_name` не задан намеренно.** На darwin имя обязано иметь вид
`utunN` — `fmt.Sscanf(options.Name, "utun%d", &ifIndex)`, иначе старт падает с
`bad tun name`. Если поле пустое, sing-box сам подставит первый свободный
`utunN`. Задавать его вручную — только повышать риск конфликта с Hiddify.

**Чего на macOS не будет:** `auto_redirect` (Linux+nftables; на darwin реализация
— заглушка, возвращающая `os.ErrInvalid`, то есть `"auto_redirect": true` = ошибка
старта), `include_interface`/`exclude_interface`, все `include_uid`/`exclude_uid`,
`platform.http_proxy` (работает только в графических клиентах).

## DNS

### Почему у `dns-ru` нет `detour`, а у `dns-proxy` есть

```json
{ "type": "udp", "tag": "dns-ru", "server": "77.88.8.8" }
```

Это не забывчивость. В новом формате DNS-серверов (1.12+) сервер **по умолчанию
использует прямой dialer** — документация формулирует это как «эквивалент пустого
direct outbound». Дописать сюда `"detour": "direct"` кажется логичным, но
sing-box 1.13 на этом **падает**:

```
start service: start dns/udp[dns-ru]: detour to an empty direct outbound makes no sense
```

Причём `sing-box check` эту ошибку **не ловит** — она проявляется только при
реальном запуске. Это одна из причин, по которой `preflight.sh` обязателен.

У `dns-proxy` `detour: "proxy"` нужен именно потому, что умолчание — прямое
подключение, а этот резолвер должен идти через туннель.

Это ломающее отличие от legacy-формата: раньше DNS-запросы по умолчанию шли через
**default outbound** (обычно прокси), теперь — напрямую.

### Формат серверов

Legacy-форма (`address`, `address_resolver`, `strategy`, `detour` на верхнем
уровне) устарела в 1.12.0 и **удаляется в 1.14.0**. Почти все гайды в интернете
написаны под неё. Здесь везде новый формат с обязательным `type` — конфиг
переживёт обновление на 1.14.

### `strategy: "ipv4_only"`

У вашего провайдера IPv6 нет: на `en0` только link-local `fe80::`, глобального
адреса нет, IPv6-связность не отвечает. Резолвить AAAA-записи в такой ситуации —
значит на каждый домен получать адрес, к которому невозможно подключиться, и
ждать таймаута перед откатом на IPv4.

`ipv4_only` убирает это целиком. Заодно из списка исключены 2178 IPv6-префиксов —
они бы всё равно никогда не сработали.

Если IPv6 у провайдера появится, поменяйте на `prefer_ipv4` и добавьте IPv6-часть
списка (`ipverse` отдаёт её отдельным файлом).

### `independent_cache: true`

Отдельный кеш для каждого DNS-сервера. Без этого ответ, полученный от
`dns-ru`, мог бы быть отдан на запрос, который должен был идти через `dns-proxy`,
и наоборот — с прямо противоположным набором IP-адресов. Стоит небольшого
проигрыша в производительности.

## Главный компромисс: DNS против IP-правил

Это то, о чём вы спрашивали, и здесь стоит быть точным.

**Проблема.** Правило `ip_cidr` (и `rule_set` с подсетями) принимает решение по
**адресу назначения**. Когда приложение идёт на `example.ru`, адрес ещё не
известен — сначала домен нужно разрезолвить. Значит порядок такой:

```
домен → DNS → IP → правило ip_cidr → direct или proxy
```

Если DNS-запрос ушёл через прокси, российский CDN увидит зарубежный адрес
резолвера и отдаст **зарубежный** узел. Этот адрес не попадёт в RU-список, и
российский сайт поедет через Финляндию — медленно, а иногда и с блокировкой по
геолокации (банки).

**Как решено.** Три механизма вместе:

1. **Доменный оверрайд решает раньше IP.** Правило с `rule_set: ["ru-direct-domains"]`
   стоит **выше** правила по IP-подсетям. Для `.ru`, `.su`, `.рф` и списка
   российских сервисов на других доменах решение принимается по имени — резолв
   вообще не влияет на маршрут.

2. **Эти же домены резолвятся российским резолвером.** В `dns.rules` тот же
   rule-set направлен на `dns-ru` (77.88.8.8, напрямую). CDN видит российский
   запрос и отдаёт ближайший узел — который к тому же попадает в RU-список.

3. **`action: "resolve"` для всего остального.** Правило

   ```json
   { "action": "resolve", "strategy": "ipv4_only" }
   ```

   стоит перед правилом по `ru-ip`. Оно нефинальное: резолвит домен и кладёт
   адреса в `metadata.DestinationAddresses`, после чего `ip_cidr` может по ним
   сработать. Без него домены, не попавшие в оверрайд, никогда бы не сматчились
   с RU-списком: подтверждено кодом `route/rule/rule_item_cidr.go` — `ip_cidr`
   сначала пробует `Destination.Addr`, а для доменного назначения смотрит именно
   `DestinationAddresses`, который заполняет `actionResolve`.

**Что остаётся неидеальным.** Российский сайт на домене `.com` или `.io`, не
попавший в оверрайд, будет разрезолвен через прокси. Если его CDN отдаёт разные
адреса в зависимости от геолокации резолвера — сайт уйдёт в туннель.

### Как это диагностировать

Симптом: сайт работает, но медленно, или показывает зарубежную версию,
или банк ругается на вход из-за границы.

```bash
# 1. Куда резолвится домен
dig +short example.com A

# 2. Входит ли адрес в RU-список
sing-box rule-set match -f binary /var/lib/sing-box/rulesets/ru-ip.srs 5.255.255.242

# 3. Как решил бы доменный оверрайд
sing-box rule-set match /var/lib/sing-box/rulesets/ru-direct-domains.json example.com
```

Если (2) не совпал, а (3) не сматчился — домен идёт через прокси. Проверьте,
меняется ли адрес при резолве российским резолвером:

```bash
dig +short @77.88.8.8 example.com A     # российский резолвер
dig +short @1.1.1.1   example.com A     # зарубежный
```

Разные ответы = тот самый случай. Лечится добавлением домена в
`rulesets/ru-direct-domains.json` — он попадёт и в маршрутизацию, и в выбор
резолвера сразу.

`healthcheck.sh` проверяет это автоматически на примере `yandex.ru`: резолвит
домен и убеждается, что полученный адрес входит в RU-список.

## Почему не fake-ip

Вы просили не использовать — и это правильно, но причина глубже, чем кажется,
и её стоит зафиксировать.

При fake-ip sing-box отдаёт приложению фиктивный адрес из служебного диапазона.
Казалось бы, правила `ip_cidr` должны ломаться на этом. На самом деле механика
другая: перед матчингом правил роутер **подменяет адрес обратно на домен** —
`metadata.Destination` становится FQDN, а фиктивный адрес уезжает в
`OriginDestination` (подтверждено в `route/route.go`).

Результат тот же: правило `ip_cidr` по реальному адресу назначения **не сработает
никогда**, потому что реального адреса на этапе матчинга просто нет. Сработает
только ветка `DestinationAddresses`, а её заполняет `action: "resolve"`.

То есть fake-ip не обходится «просто добавлением resolve» — при fake-ip resolve
становится **обязательным для каждого** соединения, что убивает главное
преимущество fake-ip (отсутствие ожидания резолва). Для split-tunneling по IP
эта схема бессмысленна.

Дополнительно: fake-ip требует `experimental.cache_file.store_fakeip`, иначе
соединения падают с `missing fakeip record`.

## Route: порядок правил

Порядок значим, потому что `sniff` и `resolve` — **нефинальные** действия: они не
прерывают перебор, а обогащают метаданные для правил ниже.

```
1. sniff                          определить протокол и домен
2. protocol=dns ИЛИ port=53       перехват DNS
3. ip_is_private                  локальная сеть напрямую
4. ip_cidr: loopback, link-local, multicast
5. rule_set: ru-direct-domains    доменный оверрайд напрямую
6. resolve                        домен → адреса
7. rule_set: ru-ip                российские подсети напрямую
   final: proxy                   всё остальное в туннель
```

**Отклонение от вашего задания.** Вы просили порядок «private → RU rule_set →
доменный оверрайд → proxy», то есть оверрайд после списка подсетей. Здесь он
поднят **выше** (шаг 5 против шага 7). Причина: правило по IP требует
предварительного `resolve`, а доменное — нет. Если оверрайд стоит первым, для
`.ru`-доменов резолв в маршрутизации не нужен вовсе — решение принимается по
имени. Функционально результат тот же, работы меньше. Если хотите буквальный
порядок — поменяйте местами блоки 5 и 7, конфиг останется валидным.

### Перехват DNS

```json
{ "type": "logical", "mode": "or",
  "rules": [{ "protocol": "dns" }, { "port": 53 }],
  "action": "hijack-dns" }
```

В 1.13 перехват DNS **не автоматический** — нужно явное правило. Старая
конструкция (outbound типа `dns` + `protocol: dns` → `outbound: dns`) не просто
устарела: **тип outbound `dns` в 1.13 удалён**, конфиг с ним не запустится.

Условие `OR` вместо простого `protocol: dns` взято из официальной документации:
`protocol` — это результат работы сниффера, и если он не распознал запрос,
правило не сработает. Ветка `port == 53` ловит обращения к системным резолверам
(у вас это 77.88.8.1 и 8.8.8.8) независимо от сниффера.

### Явный `ip_cidr` рядом с `ip_is_private`

`ip_is_private` документирован как «Match non-public IP», но про loopback в
документации 1.13 **не сказано ничего**. Поэтому `127.0.0.0/8`, `169.254.0.0/16`
и `224.0.0.0/4` продублированы явно — дешевле, чем полагаться на формулировку.

Вынести это правило в rule-set нельзя: в headless-правилах `ip_is_private` не
существует.

### `default_domain_resolver`

```json
"default_domain_resolver": { "server": "dns-ru", "strategy": "ipv4_only" }
```

Появился в 1.12.0. Для `direct`-outbound определяет, чем резолвятся домена
**в самом запросе**. Без него sing-box на старте пишет предупреждение
(`missing route.default_domain_resolver ... will be removed in sing-box 1.14.0`),
а в 1.14 это станет жёсткой ошибкой. Задан сразу — конфиг не сломается при
обновлении.

### `direct` объявлен явно

```json
"outbounds": [ ..., { "type": "direct", "tag": "direct" } ]
```

Неявного `direct` не будет. Автосоздание срабатывает только когда outbound по
умолчанию вообще не определился; как только есть `route.final`, fallback не
создаётся, и ссылка на `direct` упадёт с `outbound not found: direct`.

## Rule-set: почему local, а не remote

Список подключён как **локальный файл**, который обновляет наш скрипт:

```json
{ "type": "local", "tag": "ru-ip", "format": "binary",
  "path": "/var/lib/sing-box/rulesets/ru-ip.srs" }
```

Причины, по которым это лучше `type: remote`:

1. **Проблема курицы и яйца исчезает.** При `remote` sing-box скачивает список
   сам, и надо думать про `download_detour`, чтобы закачка шла мимо туннеля.
   У нас качает внешний скрипт: если демон работает — закачка идёт через туннель
   (это нормально), если не работает — TUN не поднят и трафик идёт напрямую
   (тоже нормально). Ни один сценарий не зависит от содержимого списка.

2. **Валидация до применения.** Скрипт компилирует список во временный файл,
   проверяет его якорными адресами и только потом атомарно подменяет рабочий.
   Битый список физически не может попасть в конфиг. При `remote` sing-box
   применил бы что скачалось.

3. **Откат.** Предыдущая версия сохраняется как `ru-ip.srs.prev`.

4. **Автоматическая перезагрузка.** Локальный rule-set перечитывается при
   изменении файла (с 1.10.0) — перезапуск демона не нужен.

Пункт 4 особенно важен в сравнении с вариантом `route_exclude_address_set`
(см. ниже): там обновление списка **не подхватывается вообще**.

`format: "binary"` для `ru-ip` — скомпилированный `.srs` (37 КБ против 152 КБ
исходника). Для `ru-direct-domains` оставлен `source`: файл маленький, зато его
можно править обычным текстовым редактором без перекомпиляции.

### `experimental.cache_file`

Строго говоря, при локальных rule-set он не обязателен. Оставлен включённым, так
как хранит служебное состояние между перезапусками и ничего не стоит. Путь задан
абсолютным: относительный резолвился бы от рабочего каталога, а у LaunchDaemon
он задаётся флагом `-D`.

## Про вариант с `route_exclude_address_set`

Это второй способ, который вы просили замерить. Здесь — почему основным выбран
не он.

**Замер на ваших данных.** RU-список после схлопывания — 8639 префиксов. Но
`route_exclude_address_set` не добавляет маршруты для исключений: он
маршрутизирует в туннель **всё остальное**, а «всё остальное» после вычитания
8639 дыр из адресного пространства распадается на:

```
дополнение 0.0.0.0/0 minus RU        = 21 652 CIDR
дополнение minus (RU + private)      = 21 724 CIDR
```

Это против 8 маршрутов сейчас. Каждый ставится отдельным `RTM_ADD` в цикле при
**каждом** старте демона.

**Второй недостаток, менее очевидный и более серьёзный.** На macOS набор
исключаемых подсетей снимается **снимком при старте**. Обновление rule-set
маршруты не пересчитывает: callback регистрируется только при живом
`auto_redirect` (`if t.autoRedirect != nil` в `protocol/tun/inbound.go`), а
`auto_redirect` существует только на Linux. Более того, обработчик
`updateRouteAddressSet` безусловно вызывает `t.autoRedirect.UpdateRouteAddressSet()` —
он физически рассчитан только на nftables-путь.

Значит после каждого обновления списка вариант (а) требует перезапуска демона —
то есть разрыва всех соединений. Вариант (б) подхватывает новый файл сам.

Плюс варианта (а) один, но настоящий: RU-трафик не заходит в sing-box вообще,
экономя обработку в userspace.

## Log

```json
"log": { "level": "warn", "timestamp": true }
```

`output` не задан намеренно — вывод идёт в stdout, а перенаправлением занимается
launchd через `StandardOutPath`. Обратная сторона: launchd держит дескриптор
открытым, и после ротации `newsyslog` записи продолжат идти в архивный файл.
Подробности и обходной путь — в комментариях `launchd/sing-box.newsyslog.conf`.
При уровне `warn` лог растёт медленно, так что ротация случается редко.
